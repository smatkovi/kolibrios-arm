# Bringing it up on the N950

Nothing of this has run on the device yet. The steps, in the order that
risks least:

## 1. What the display looks like under Linux

On the N950 under Harmattan or Leste, as root:

```sh
sh tools/n950-dss-dump.sh > dss.txt
```

It only reads registers. `kernel/platform/n950.c` assumes that the boot
loader leaves DISPC's graphics layer on a frame buffer in RAM (DISPC_GFX_BA0,
its size in DISPC_GFX_SIZE, a 16 or 32 bit format) and that the DSI link
to the panel stays up, so that DISPC_CONTROL's GOLCD and LCDENABLE send
one frame (command mode panels work frame by frame). The dump shows
whether that holds, and what NOLO itself sets.

## 2. Start from RAM, without writing the flash

NOLO loads a kernel into RAM and starts it, from the PC over USB:

```sh
0xFFFF -m build/n950/kernel.bin -l -b        # or Nokia's flasher: -k ... -l -b
```

(the N950 switched off, connected while the tool waits). The image is
linked at 0x80008000, where NOLO puts a kernel. It writes nothing to the
flash; switching off brings the phone back to its own system.

What to expect: the KolibriOS desktop on the screen (the panel, the
example window, the clock). A kernel panic shows its message in a red
bar at the top of the screen, since there is no serial port at hand.
Keyboard and touch screen are written but untried: the kernel's
debug board (`board` in the menu) says whether the maXTouch and the
keypad answered, and the touch directions may need turning.

## 3. From ubiboot, next to Leste

The image carries a zImage head (magic 0x016f2818 at 0x24), so ubiboot
starts it like a Linux kernel. smatkovi/n950-maemo-leste's image puts it
on Leste's partition: `KOLIBRI_BIN=build/n950/kernel.bin` for its
`rootfs/build.sh` copies it to p4's `/boot/kolibri.bin` (the release
images from leste-20261029 on have it), and its `install/n950-install.sh`
then makes KolibriOS the second kernel line of ubiboot's "Maemo" entry:

    G_OS5_NUM=2
    G_OS5_AUTOBOOT=0                # ubiboot asks which line; 1 = Leste at once
    G_OS5_2_LABEL="KolibriOS (test)"
    G_OS5_2_FILE="/boot/Maemo/boot/kolibri.bin"

(`/boot/Maemo` is ubiboot's link to the mounted p4.) Choosing it, ubiboot
runs `kexec -l <file> --type=zImage --command-line=...` and `kexec -e`
with its kexec-tools 2.0.3: the image goes to the lowest free RAM plus
0x8000, that is 0x80008000 where it is linked, the ATAGs to 0x80001000
(r2; ignored here, as is the command line from Leste's `/boot/cmdline`),
MMU and caches off. Before that, ubiboot's own kernel (2.6.32, omapfb) has
the panel on and DISPC's graphics layer on its frame buffer near the top
of the 1 GiB, outside the 256 MiB this kernel uses; `n9_display_init`
maps that buffer uncached and draws into it.

Order for the first test on the phone:

1. Under Leste (or Harmattan), as root: `sh tools/n950-dss-dump.sh >
   dss.txt` (step 1; Leste's kernel has /dev/mem). It shows the
   display as a Linux left it, which is what this kernel takes over.
   ubiboot's omapfb is another Linux than the one that made the dump, so
   the dump says what to expect rather than what ubiboot leaves.
2. Reboot into ubiboot, choose "Maemo", then "KolibriOS (test)".

What it should show: KolibriOS's Hildon-style desktop in landscape (the
status bar with the application button at the top left and the clock,
the clock widget, the hint "The applications: the button at the top
left"), as `make run` shows it in QEMU. Panics show their text in a red
bar at the top. The turn of the picture (`n9_display_flush`) and the
touch directions are guesses until seen; the keyboard and the touch
screen are polled and untried; the debug board (`board`, from the
application menu) says whether the maXTouch and the keypad answered.
There is no RTC driver yet: the clock starts at 00:00 on 1 January 1970.

Back: hold the power key until the phone switches off, then start it
again; nothing of this writes the flash or the eMMC, Leste and Harmattan
stay as they were.

From a running Leste instead (no ubiboot menu, the display as Leste's
omapdrm left it): `apt install kexec-tools`, then `kexec -l --type=zImage
/boot/kolibri.bin && sync && kexec -e`. Untried as well.

## 4. The bench: `kolibri.bench` (docs/asm.md, part 4)

The drawing loops, the flush and memcpy/memset timed on the device, C
against NEON, before the first program starts. It needs only the
display (step 1's findings); the results go onto the screen, since
there is no serial port at hand. From the image with ubiboot's
"KolibriOS (test)" line (step 3), with a running Leste.

On the PC, a kernel with the arguments built in (ubiboot hands
KolibriOS Leste's own `/boot/cmdline`; those come after these):

```sh
make PLATFORM=n950 CMDLINE="kolibri.bench kolibri.run=/sys/board"
scp build/n950/kernel.bin root@<N950>:/boot/kolibri-bench.bin
```

On the N950 under Leste, as root (the image's KolibriOS kept aside):

```sh
cp /boot/kolibri.bin /boot/kolibri-test.bin
cp /boot/kolibri-bench.bin /boot/kolibri.bin
sync
reboot
```

In ubiboot: "Maemo", then "KolibriOS (test)".

What it should show, a second or two after the choice: a black
screen with 16 lines (8x16, the first and the last green), in
landscape if the flush's turn is right (else turned or mirrored, still
readable):

```
bench: 854 x 480, 1000000000 Hz counter, best of 5; C, then assembler (NEON)
bench: fill, everywhere:           C ... us, asm ... us, N.Nx, ... MB/s
bench: fill, a window's 2/3:       ...
bench: fill, the covered 1/3:      ...
bench: text 8x16 on its colour:    ...
bench: text 6x10, no background:   ...
bench: image 9 x 270x136 (fn 7):   ...
bench: read a quarter (fn 36):     ...
bench: turn to RAM, 32 bpp:        ...
bench: turn to RAM, 16 bpp:        ...
bench: memcpy 2 MiB:               ...
bench: memcpy 2 MiB, d+4:          ...
bench: memset the owner map:       ...
bench: the flush (display):        C ... us, asm ... us, N.Nx, ... MB/s
bench: the flush, by columns (old): ... us, ... MB/s
bench: done, the screen kept for 20 s (kolibri.benchhold=S)
```

Photograph it: it stays 20 s (`kolibri.benchhold=60` in `CMDLINE` for
longer). Then the Hildon desktop, the debug board over it with the
boot log: `command line: kolibri.bench kolibri.run=/sys/board` and
Leste's arguments, `VFP/NEON: FPSID 410330c3, ...` (the Cortex-A8 r3),
`drawing: NEON`, the bench lines again.

Reading it: the first line's rate is the CPU's clock as ubiboot's
Linux left it (1 GHz at the N950's top operating point, less at a
lower one); `32768 Hz counter` means the cycle counter did not run
and the times are in 30 us steps. The fills and the pictures should be
several times faster with NEON, the turns to RAM too; `the flush
(display)` writes the uncached frame buffer by whole panel lines (C
and NEON alike, the bus decides), `the flush, by columns (old)` the
way the kernel did before: the difference between those two is the
memory system's. A line with `asm` slower than `C` is the thing to
report. Nothing on the screen: the display's takeover (step 1) is the
first suspect, as for any KolibriOS start. A reset after a fixed time:
a watchdog left running by the boot loader (the kernel does not serve
one).

Back: hold the power key; under Leste again, the image's KolibriOS
back in its place: `cp /boot/kolibri-test.bin /boot/kolibri.bin`.

The same in QEMU's realview (800 x 480, no flush line; meaningless
times):

```sh
make CMDLINE="kolibri.bench kolibri.run=/sys/board"    # or QEMU_APPEND= with the plain build
python3 scripts/qemu-shot.py build/realview/kernel.bin /tmp/b wait:3 shot:bench wait:25 shot:board
```

## 5. The eMMC (docs/storage.md)

The kernel switches MMC2's clocks and the eMMC's supply on, resets the
controller and starts the card anew; MyDocs is `/mmc0/1`, Harmattan's
root `/mmc0/2`, Leste's `/mmc0/4`, all read only. The debug board shows
`blk: mmc0: eMMC ...` and the partitions; nothing is written without the
container (`tools/kolibri-home` under Leste) and `kolibri.home=rw`.
`kolibri.storage=off` leaves the eMMC alone. The steps for the device:
`docs/storage.md`.

## 6. Random numbers (docs/rng.md)

The OMAP3630's RNG is behind the secure side's firewall on the N950 (an
HS device); the kernel asks Nokia's PPA for its output as Harmattan's
kernel did (service 29, `smc #1`): **untried**, `kolibri.romrng=off`
leaves the PPA alone. Without it the seed comes from the timing jitter
of the cycle counter against the 32 kHz crystal, and the console says
`rng: WEAK` at every start: nothing that needs a secret key then. The
check for the device (`make PLATFORM=n950 CMDLINE=kolibri.rngtest`) and
what it may show: `docs/rng.md`, "On the devices".
